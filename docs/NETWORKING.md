# Сеть: путь трафика

```
приложение ──IP-пакеты──► TUN 10.240.0.1/24 (MTU 1500)
                             │ VpnTunPacketHandler (поток tun-reader, poll)
             ┌───────────────┼─────────────────────────┐
           TCP              UDP :53                 прочий UDP / ICMP / IPv6
             │                │                         │
     TcpProxySession     DNS-over-TCP              ICMP port unreachable / отброс
             │                │
             └──► Socks5Client ──► Socks5ProxyServer 127.0.0.1:<socksPort>
                                        │ TunnelTransport.openStream(host, port)
                                        ▼
                               SshTunnelClient (JSch) ── direct-tcpip ──► шлюз ──► цель
```

## Конфигурация TUN (`SshVpnService.establishTun`)

- Адрес `10.240.0.1/24`, MTU 1500, DNS — из настроек (по умолчанию `1.1.1.1`), неблокирующий fd.
- **IPv6 не настраивается** → Android блокирует IPv6 выбранным приложениям, они идут по IPv4.
- Маршруты:
  - обход LAN выключен — `0.0.0.0/0`;
  - включён (по умолчанию) — дополнение к `Cidr.PRIVATE_NETWORKS` (10/8, 172.16/12, 192.168/16,
    169.254/16, 224/4, 255.255.255.255) — около 67 префиксов (`Cidr.complement`). Если DNS-сервер
    сам в частной сети, для него добавляется `/32`, чтобы DNS не ушёл мимо тоннеля.
- Приложения: `ROUTE_ONLY_SELECTED` → `addAllowedApplication` для выбранных; `ROUTE_ALL_EXCEPT` →
  `addDisallowedApplication` для выбранных и для самого приложения. Своё приложение в тоннель не
  попадает никогда (SSH-сокет дополнительно `protect()`).
- `setMetered(false)` (API 29+), иначе система считает соединение лимитным.

## TCP: `vpn/net/TcpProxySession`

Userspace TCP-конечная точка на каждое соединение приложения (ключ `FlowKey`).

- SYN → соединение с SOCKS5 (`Socks5Client.connect`) **до** ответа SYN-ACK. Ошибка → RST, приложение
  сразу получает отказ.
- SYN-ACK с MSS 1460 и window scale 0 (если клиент прислал WS). Наше окно приёма ≤ 65535 и
  уменьшается, пока данные приложения ждут записи в SOCKS-сокет.
- Приём: только по порядку; дубли и перекрытия обрезаются, данные вне порядка — dup-ACK.
- Отправка: не больше `min(окно клиента << wscale, 256 КБ)` неподтверждённых данных
  (`ByteQueue`), сегменты по MSS.
- Повтор: RTO 400 мс → ×2 до 6 с, после 10 повторов — RST. Нулевое окно — проба `SND.NXT-1` раз в секунду.
- Полузакрытие в обе стороны: FIN приложения → `shutdownOutput` в SOCKS; EOF от сервера → наш FIN.
  Сессия закрывается после обмена FIN или через 60 с тишины в полузакрытом состоянии.
- Пакет для неизвестного соединения (например, после перезапуска) → RST.
- Потоки: один поток чтения на сессию + задача записи только пока есть данные. Пулы —
  собственные `Executors.newCachedThreadPool` (стек 256 КБ), **не** `Dispatchers.IO`.
- `tick()` вызывается раз в 200 мс таймером обработчика.

## DNS

- UDP на порт 53 **любого** адреса: запрос уходит DNS-over-TCP (RFC 7766) через SOCKS5 на тот же
  адрес, ответ возвращается от его имени.
- `DnsCache`: 512 записей, ключ — вопрос без ID (регистр имени не важен), TTL = минимальный TTL
  ответа в пределах 10–600 с, TTL в выдаче уменьшаются; кэшируются только успешные ответы.
- Ответ > 512 байт клиенту без EDNS — заголовок + вопрос с флагом TC (клиент повторит по TCP,
  который тоже идёт в тоннель).
- Параллельно не больше 32 запросов; лишние отбрасываются (резолвер повторит).

## SOCKS5: `Socks5ProxyServer`

- Слушает `127.0.0.1:<socksPort>` без аутентификации, только CONNECT. `socksPort = 0` в профиле —
  свободный порт от системы при каждом подключении (`boundPort`, наружу — `SshVpnService.socksPort`);
  адреса IPv4/IPv6/домен (домен резолвится на шлюзе).
- Переживает переподключения SSH: пока сессии нет, CONNECT сразу отвечает ошибкой.
- Два потока на соединение (загрузка/выгрузка), полузакрытие передаётся в обе стороны.
- Единственное место подсчёта трафика для статистики.
- Порт доступен любому приложению на устройстве — это функция «`ssh -D` для приложений с поддержкой
  прокси», но учитывайте это при работе с конфиденциальными сетями.

## SSH: `SshTunnelClient`

- JSch (`com.github.mwiede:jsch`) + BouncyCastle (Ed25519, curve25519).
- `StrictHostKeyChecking=no` — ключ хоста не проверяется (известная доработка: TOFU/known_hosts).
- Шифры: AES-GCM в приоритете, затем AES-CTR. TCP_NODELAY и keepalive на сокете, `protect()`.
- Keepalive: интервал из профиля (режим экономии — не меньше 60 с), 3 пропуска = обрыв.
  `setServerAliveInterval` вызывается **после** установки `timeout`.
- Аутентификация задаётся `AuthType.sshMethods` (`PreferredAuthentications`), ключ всегда раньше
  пароля: `PASSWORD` → `password,keyboard-interactive`; `PRIVATE_KEY` → `publickey`;
  `PRIVATE_KEY_AND_PASSWORD` → `publickey,password,keyboard-interactive`. Последний вариант
  работает и как запасной (ключ не принят — пробуется пароль), и для серверов с
  `AuthenticationMethods publickey,password` (нужны оба: после частичного успеха по ключу сервер
  просит пароль).
- `PasswordPromptAnswerer` отвечает на `keyboard-interactive` сохранённым паролем, если запрос один
  и скрытый. Без него JSch отвечает только на запрос, содержащий `password:`. OTP и многошаговые
  запросы не поддерживаются (будет «Auth fail»).
- Зашифрованный ключ расшифровывается заранее: `addIdentity(..., passphrase)`.
- Ошибки аутентификации (`isPermanentFailure`) не повторяются.
- `disconnect()` прерывает и идущее подключение (закрывает сокет фабрики).

### Управление потоком каналов (важно)

JSch принимает данные всех каналов в одном сессионном потоке и сразу же снова открывает окно SSH.
Если читатель одного канала медленный (видеоплеер с полным буфером), сессионный поток блокируется
и **встают все соединения**. Поэтому:

- у `direct-tcpip` выход канала — `SshChannelBuffer.sink`, который никогда не блокирует;
- при буфере ≥ `window/2` вызывается `ChannelWindowControl.pause` (окно этого канала больше не
  пополняется), при ≤ `window/8` — `resume` (посылаем `SSH_MSG_CHANNEL_WINDOW_ADJUST` сами);
- окно канала 512 КБ (у JSch по умолчанию 128 КБ), максимальный пакет 32 КБ.

`ChannelWindowControl` лежит в пакете `com.jcraft.jsch` ради доступа к package-private полям.
При обновлении JSch сверяйте `Session` (обработка `SSH_MSG_CHANNEL_DATA`) и поля `Channel`
(`lwsize`, `lwsize_max`, `lmpsize`, `close`).

## Переподключение и смена сети

- `registerDefaultNetworkCallback` (приложение исключено из тоннеля, поэтому это нижележащая сеть).
- Сессия жива, а сеть сменилась (Wi-Fi ↔ Ethernet) → переподключение сразу.
- Во время паузы между попытками смена сети будит цикл досрочно.
- Всё это время TUN поднят: выбранные приложения получают RST, но не ходят напрямую.

## Внешний IP на главном экране

- `vpn/net/GeoIpLookup` — чистый Kotlin: мини-HTTP(S) поверх переданного сокета (`MiniHttp`, TLS с
  проверкой имени хоста), разбор JSON (`MiniJson`), цепочка сервисов `ipwho.is` → `ipinfo.io` →
  `ip-api.com` (последний только по HTTP). Название страны берётся из ответа или из `Locale` по коду
  страны, язык — язык устройства (`ru`/`en`, остальные → `en`).
- Пока тоннель подключён, запрос идёт через локальный SOCKS5 (`Socks5Client.connectHost`, имя
  хоста резолвится на стороне шлюза). Наше приложение исключено из тоннеля, поэтому обычный HTTP-запрос
  показал бы реальный IP устройства, а не выходной адрес SSH-сервера.
- Без тоннеля — прямое соединение, на карточке пометка «напрямую».
- `MainViewModel.refreshExternalIp`: перепроверка при смене состояния тоннеля, кэш 5 минут на путь
  (`direct` или `tunnel:<serverId>:<фактический socksPort>`), кнопка «обновить» принудительно. Во время
  подключения/переподключения значение не трогается.
- Запрос уходит стороннему сервису — при работе в закрытой сети без выхода в интернет карточка
  покажет «Не удалось определить внешний IP».
